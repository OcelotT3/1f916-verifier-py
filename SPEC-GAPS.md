# SPEC-GAPS — 1F916 Protocol, commit 728e33e (spec text only)

Found while building a clean-room verifier from `SPEC.md` (sha256 998b1b1f…e339), `draft-maintainer-1f916-agent-record-01.txt` (a0a13891…bda9c) and `witness-rotate-v1.json` (60e482d5…8ebf), plus a live run against https://1f916.ai on 2026-10-07 ~09:58 PT. **No reference code was consulted**; where the text is silent we chose an assumption, tagged `[G-n]` in `verifier.py`.

Risk = how plausibly a second independent implementer decides differently (→ different verdicts / digest).

## Top gaps (ranked)

### G-2 — "dossier core" is never defined; the live dossier signature does not verify under any reading we tried — **HIGH** (also a live mismatch)
- **Where:** SPEC §8 ("signs `1f916.record.v1:<sha256-hex of JCS(dossier core)>`"), draft §3.6 ("SHA-256 of the JCS-canonical dossier core"). The served `registry_sig.over` repeats `sha256(JCS(dossier-core))`; `seals_note` says the seals view is "not part of the signed core"; `caps_note` says "the signed core carries what this page carries".
- **Live result:** `GET /api/record/1f916-agent` → `registry_sig.sig` does **not** verify under the spec-published key over our reading. Brute-force over the served top-level members: every core = (all 30 members − registry_sig) minus any ≤6 of the 25 non-essential members (≈245k candidates, `handle,keys,events,checkpoint` always kept), and every core = those four + ≤7 others that we got through before the time limit. **No match.** The checkpoint signature in the same dossier, and all 191 event inclusion proofs, *do* verify, so the key, the JCS code and the payload prefix are probably fine. Most likely the core has a shape that is not a member-subset of the served JSON (renamed or restructured members, or events/attestations in a different form).
- **Ours or theirs?** We can't decide that from the spec. It's a spec gap either way: nobody can re-check the dossier signature from the text. If the core is in fact a subset we missed, that is our miss. We did not look at the reference code to find out.
- **Assumption:** core = dossier minus `registry_sig`, `seals*` (labelled outside the core), `now`, `now_utc`. Verdict = `diverged`, and the run names the exact check that failed.
- **Proposed wording:** "The dossier core is the JSON object consisting of exactly the members M1…Mn (listed), with each member's value exactly as served. All other members, including `registry_sig`, `now`, `now_utc`, `*_note`, and `seals*`, are outside the core. A test vector (dossier + core bytes + digest + signature) is published at testvectors/record-core-v1.json."

### G-6 — The decision digest (§8a.1) is not defined precisely enough to implement — **HIGH**
- **Where:** SPEC §8a.1: "the canonicalized accept/reject outcome for every row, summarized in one hash."
- Not defined: what a *row* is (an event? a checkpoint? an attestation?), the corpus format, the accept criteria per row type, the row identifier, ordering, the canonical form (JCS? JSONL?), the hash (sha256?), how legacy/unsealed rows count, and whether the run verdict feeds into row outcomes. No frozen corpus or expected digest is published at 728e33e.
- **Assumption:** row = one log event `(log, id)`. Accept iff the row has an inclusion proof that verifies against a checkpoint whose signature verifies under the caller-supplied registry key; otherwise reject (legacy_unsealed counts as reject). If the same row appears twice, it is rejected if any copy fails. Digest = `sha256_hex(JCS([{"log","id","decision":"accept"|"reject"}…] sorted by (log,id)))`. Live: 201 rows, 192 accept, digest `788bacfc…5994`.
- **Proposed wording:** define the corpus file format and the row = (log, event id). Give the accept predicate in pseudo-code, the encoding `JCS(array sorted by log then id)` and SHA-256 lowercase hex, and publish corpus + expected digest together.

### G-1 — Four verdicts or five? — **HIGH**
- **Where:** draft §3.6 "Verifiers MUST implement a four-valued verdict" (witnessed / consistent-unwitnessed / unanchored / diverged). SPEC §8 "Five verdicts" adds `witness-unusable` and says a verifier "MUST NOT report this as consistent-unwitnessed".
- One implementer following the draft emits `consistent-unwitnessed` where another emits `witness-unusable`. That is a guaranteed digest or verdict split.
- **Assumption:** five verdicts (SPEC §8 is the stricter text and carries a MUST NOT). Exit codes: witnessed 0, diverged 1, usage 2, consistent-unwitnessed 3, witness-unusable 4, unanchored 5 (exit codes are unspecified, SPEC says only "SHOULD be distinct").
- **Proposed wording:** make the two texts say the same thing ("five-valued"). Define precedence: diverged > unanchored > witness-unusable/witnessed > consistent-unwitnessed. Define the exit-code table normatively.

### G-4 — "Continuity" of a countersignature has no defined field, and isn't signed — **HIGH**
- **Where:** SPEC §6(1), draft §3.3/§3.6 ("countersignature asserts continuity from a previously observed head"). The countersignature payload `1f916.witness.v1:<origin>:<log>:<size>:<root>` does not cover continuity, status or created_at.
- **Live:** commonwealth lines carry `"consistency":"verified from 24194"` or `"first observation"`. glm-flash lines (witness 11) have **no `consistency` field at all**. Refusals are described as unsigned. So whoever hosts a witness file can turn "first observation" into "verified from N" without breaking any signature, and can inject unsigned refusal lines that MUST fail the run (a cheap DoS).
- **Assumption:** continuity ⇔ the `consistency` string starts with `"verified from"`. A missing field or anything else ⇒ no continuity ⇒ at best `witness-unusable`. Any refusal line for (origin, log, size) ⇒ `diverged`.
- **Proposed wording:** define the countersignature line schema (field names, enum values). Put continuity into the signed payload, e.g. `1f916.witness.v2:<origin>:<log>:<size>:<root>:<prev_size>`, with `prev_size=0` meaning first observation. Sign refusals.

### G-5 — The event-hash preimage is undefined, so event content and the hash chain can't be verified — **HIGH**
- **Where:** SPEC §3 "each event carries the hash of its predecessor"; draft §3.2 "a linear hash chain enabling full-replay verification". No formula for `hash` from (prev_hash, kind, detail, created_at, …) is given.
- Consequence: an inclusion proof only shows that the 64-hex string is in the log. It doesn't show that `kind`/`detail`/`created_at` are what was logged. `prev_hash` can't be checked either, because dossier events are a non-contiguous per-agent subset of a global log (live: event 15 has `leaf_index` 0 and `prev_hash` = 64 zeros).
- **Assumption:** we don't verify event content and we say so in the "does NOT prove" output.
- **Proposed wording:** "hash = SHA-256 hex of UTF-8(`1f916.event.v1:` + prev_hash + `:` + JCS({…members…}))", with a test vector.
